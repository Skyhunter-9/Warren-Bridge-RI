PROGRESS MADE:
- Clarified the actual goal: a live capture pipeline that intercepts
  structural-monitoring data from a third-party vendor site (GeoCloud /
  geo-instruments.com) and feeds it into the dashboard, since the vendor
  doesn't offer a public API. Established a "teach me, don't just build it"
  collaboration mode with a running, repeatedly-reposted step-by-step
  syllabus.
- Installed Playwright (@playwright/test) and Chromium, and separately
  @microsoft/signalr / @microsoft/signalr-protocol-msgpack after identifying
  (via F12 DevTools) that GeoCloud's live data arrives over SignalR using the
  MessagePack sub-protocol.
- Attempted a direct browser-side SignalR connection first (the simplest
  option) - hit a CORS wall specific to a redirect during the connection's
  preflight check.
- Pivoted to running the same connection logic as a standalone Node script
  (installed tsx as a devDependency to run TypeScript directly) - the browser
  CORS restriction doesn't apply outside a browser, which got past that wall
  and revealed the real blocker underneath: a 401 Unauthorized response.
- Investigated the site's real auth mechanism by inspecting a successful,
  logged-in request's headers - confirmed cookie-based ASP.NET Core Identity
  authentication (not a bearer token), which can't be faked from a bare
  script and requires an actual browser login.
- Rebuilt the approach around Playwright: launched a real, visible Chromium
  browser, used page.pause() to hand control to the user for a one-time
  manual login, then resumed the script programmatically.
- Attached page.on("websocket")/framereceived listeners and confirmed real
  WebSocket frames were arriving once navigation was pointed directly at a
  graph URL instead of the site's Projects listing page.
- Successfully decoded real SignalR messages using
  MessagePackHubProtocol.parseMessages() - confirmed the hub method name
  ("UpdateGraph"), the SignalR message-type numbering (1=Invocation,
  3=Completion, 6=Ping), and that GeoCloud pushes an entire week of hourly
  historical readings per update, not a single live point.
- Based on that hourly/bulk-historical shape, decided this data belongs in
  the app's existing CSV-style batch-merge ingestion pattern rather than the
  live 1Hz snapshot buffer.
- Discovered Easting and Northing readings live on two separate graphs from
  the Z-axis one already captured, and found those graph URLs too.
- Designed a pattern for watching all three axis-graphs with a single login:
  one shared Playwright browser context, three separate pages (tabs), all
  authenticated together once login succeeds on any one of them.

PROBLEMS & REMEDIATIONS:
1. Problem: Browser-side SignalR connection blocked by CORS
   ("Redirect is not allowed for a preflight request").
   Fix: Ran the identical connection code as a plain Node script instead,
   which isn't subject to browser CORS rules at all.
2. Problem: Node script got 401 Unauthorized - no browser session to
   authenticate with.
   Fix: Identified the site uses cookie-based session auth (not a token) and
   switched approach to a real, Playwright-driven browser login.
3. Problem: Top-level `await` failed ("not supported with the cjs output
   format") when running the Playwright script via tsx.
   Fix: Wrapped the script body in `async function main() { ... }` and called
   it at the bottom instead of using bare top-level await.
4. Problem: ESLint's no-floating-promises rule flagged the bare `main();`
   call at the bottom of the script.
   Fix: Changed to `main().catch((err) => console.error(...))` so errors
   inside main() are actually surfaced instead of becoming a silent
   unhandled rejection.
5. Problem: The capture script only ever landed on GeoCloud's generic
   Projects page, never actually opening a graph, so no WebSocket connection
   was ever observed.
   Fix: Pointed `page.goto(...)` directly at the specific graph's own deep
   URL (discovered via the request headers), instead of the site root -
   ASP.NET's login-redirect flow correctly bounces back to that URL after
   login.

PROGRESS MADE:
- Extended the capture script to watch all three axis-graphs (Z, Easting,
  Northing) simultaneously, each in its own Playwright page, all sharing one
  authenticated browser context so only one manual login is needed per run.
- Confirmed GeoCloud's own GNSS numbering (GNSS02, GNSS03, GNSS04) lines up
  1-to-1 with the app's own SENSOR_GROUPS.gnss ordering ("GNSS 2", "GNSS 3",
  "GNSS 4").
- Designed and wrote the merge logic (`ingestUpdateGraphMessage`): parses
  each incoming UpdateGraph message's sensor names with a regex, converts
  GeoCloud's 1-based numbering into the app's 0-based node index, and
  accumulates readings into a Map of rows keyed by timestamp so all three
  axes end up combined into one row per moment, matching the app's
  `gnss_<nodeIndex>_<axis>` field-naming contract.
- Wired the merge function into the live frame-decoding path (only for real
  "UpdateGraph" Invocation messages, not pings/completions) and confirmed it
  actually works: 168 accumulated rows (7 days x 24 hours), an exact match
  for the real capture window.

PROBLEMS & REMEDIATIONS:
1. Problem: `noopLogger` used before it was actually declared - the parseMessages
   helper referenced a name that only existed as a typo (`constnooplogger`,
   missing a space) so nothing was ever really declared under the name being used.
   Fix: Corrected the declaration syntax.
2. Problem: A method-name typo, `pareseMessages`, and a missing import of
   `MessagePackHubProtocol` caused further "cannot find name" errors.
   Fix: Corrected the typo and added the missing import.
3. Problem: TypeScript flagged the Buffer-to-ArrayBuffer conversion needed
   before decoding, since `Buffer.buffer` is typed as `ArrayBuffer |
   SharedArrayBuffer`, not plainly `ArrayBuffer`.
   Fix: Added an `as ArrayBuffer` type assertion, since a SharedArrayBuffer
   genuinely never occurs in this context - a legitimate use of a type
   assertion, not a workaround for a real bug.
4. Problem: ESLint's no-unnecessary-type-assertion rule then flagged that
   same assertion as pointless, contradicting the real compiler error that
   required it.
   Fix: Identified this as a known blind spot where ESLint's own type
   inference (via a shared @itwin/eslint-plugin preset) disagrees with the
   real TypeScript compiler; kept the assertion (required for the actual
   build to succeed) and silenced just that one ESLint rule with a disable
   comment.
5. Problem: The very first captured frame threw "Incomplete message" from
   the MessagePack decoder.
   Fix: Wrapped frame parsing in try/catch so one bad frame doesn't crash the
   whole capture session; confirmed via testing this was a harmless one-time
   startup artifact, not a systemic fragmentation problem worth building
   complex frame-reassembly logic for.
6. Problem: When watching all three graphs at once, only one tab (whichever
   the user happened to log into) ever successfully authenticated - the
   other two stayed stuck on their own login-redirect pages forever, since
   logging in on one tab doesn't retroactively re-navigate tabs that already
   loaded a stale page before the login happened.
   Fix: Restructured the script to open only the Z tab first, log in through
   it, and only open the E and N tabs afterward - by then the session cookie
   is already valid, so their first navigation succeeds without ever hitting
   a login redirect.

PROGRESS MADE:
- Renamed the app's "CSV" ingestion mode to "Periodic" across
  sensorIngestion.ts, IoTDashboard.tsx, chartData.ts, Sensor3DDisplay.tsx, and
  CLAUDE.md, to remove the misleading implication that this mode requires
  downloading files - it never did; it's a periodic-fetch-and-merge pattern
  that happens to use CSV-formatted text as its wire format. Kept the actual
  CSV text-parsing utilities (parseCsv/csvToFlatRows/FlatCsvRow) named as-is,
  since that part of the description remains accurate.
- Built a small standalone HTTP server (Node's built-in `http` module, no new
  dependency) inside the capture script, generating CSV-formatted text live
  from the in-memory accumulated GNSS rows on every request - no files are
  ever written to disk.
- Wired the real app's SENSOR_INGESTION.gnss entry to point at that server
  (mode: "Periodic", url: "http://localhost:4000", pollIntervalMs: 1 hour).
- Confirmed (via direct testing, not just inspection) that the capture
  script's server was serving real, correctly-shaped GNSS data end to end.
- Fixed a chart-flooding bug: the live 1Hz snapshot buffer always contains a
  value for every sensor field, every second, even for Periodic-mode types
  (SensorService can't leave a field empty) - this was flooding
  Periodic-mode charts with meaningless per-second noise alongside the real
  hourly data. getMergedChartData now skips the live buffer entirely when a
  chart's types are all Periodic-mode.
- Found and fixed a much deeper, pre-existing bug: vite.config.mts had
  customized Vite's `envPrefix` to "IMJS_" only (for Bentley's own auth
  variables), which silently replaced Vite's default "VITE_" prefix instead
  of adding to it - meaning every `VITE_`-prefixed .env variable
  (VITE_SENSOR_MODE, all the vendor URLs) had never actually reached the
  browser at all, project-wide, since the sensor-mode feature was first
  built. Fixed by setting envPrefix to `["IMJS_", "VITE_"]`.
- Added a CORS header (`Access-Control-Allow-Origin: *`) to the capture
  script's own local server - it's a different port (4000) than the
  dashboard (3000), which counts as a different origin under browser CORS
  rules, the same category of problem as the original GeoCloud CORS wall,
  just against the user's own local server this time.
- Found and fixed a genuinely broken "all time" chart timeframe option:
  `getLookbackCutoff` had a case for every other timeframe except "all
  time," which silently fell through to the same 45-second default as "Real
  time" - meaning selecting "All time" had never actually shown all
  historical data, for any sensor type, the whole time. Added a real case
  for it, and changed GNSS's default timeframe from "Real time" (useless for
  hourly data) to "all time".
- Fixed a chart hover/tooltip bug: periodic data's x-axis label
  (`time: new Date(timestamp).toLocaleTimeString(...)`) only showed
  hour:minute:second, discarding the date - meaning the same label
  ("07:00:00") repeated once per day across a week of data, which broke
  Recharts' hover tracking past the first day and left the axis showing no
  date information. Fixed to include the date in the label.
- Polished the GNSS summary tile: removed the constantly-ticking E/N
  readout, retitled "Node 1 Deflection:" to "GNSS Sensors".
- Added temporary `[periodic]` diagnostic console logging to
  sensorIngestion.ts's periodic-fetch code path to definitively confirm
  (rather than guess from an ambiguous Network tab) exactly where the
  ingestion pipeline stood at each step - to be removed once everything is
  fully confirmed stable.
